# OpenAI TTS duration estimation / CoreML bucket tuning plan

## 背景 (Context)

- 大型 CoreML バケット実装はすでにデプロイされ、機能している。
- 294 文字のリクエストで以下の値が観測された:
  - `generation-seconds = 77`
  - 生成された WAV の長さ = `54.68s`
  - API 全体の所要時間 = `92.97s`
- バックエンドは `coreml-stateful` で、PyTorch フォールバックは発生していない。
- 当該リクエストで選択されたバケットは `S1024_T128_R160` と `S1536_T192_R160` の組み合わせだった。

つまり「大型バケットが使えるようになり、フォールバックも起きていない」という前提のうえで、なお生成時間が想定より長くなっている、という状態である。

## 問題定義 (Problem definition)

- 分割 (splitting) 自体は期待通り発生している。
- しかし、各セグメントの想定秒数を求める際、現在のデフォルト値は次の通り:
  - `chars_per_second = 4.0`
  - `seconds_padding = 1.5`
- このパラメータでセグメント秒数を見積もると、明らかに過大評価になる:
  - 135 文字 → 約 `135 / 4.0 + 1.5 = 35.25s` (≒ 35.5s)
  - 159 文字 → 約 `159 / 4.0 + 1.5 = 41.25s` (≒ 41.5s)
- S バケットは「想定生成秒数 × patched steps」ベースで選ばれるため、秒数を過大評価するとチャンクが必要以上に大きい S バケットに割り当てられてしまう。
- 結果として、本来 `S1024` で十分に収まるはずのチャンクが `S1536` を選択してしまうケースが発生し、生成時間が伸びる。

## 根本原因 (Root cause)

- デフォルトの `chars_per_second = 4.0` は、本デプロイにおける日本語の説明調読み上げに対して保守的すぎる。
- 実測された文字速度はおよそ `294 / 54.68 ≒ 5.37 chars/s`。
- すなわち、現状のデフォルトは実速度より約 25% 遅い前提で計算しており、これが「分割は発生したが、各チャンクの S バケットが一段大きく選ばれてしまう」現象の主因。
- バケット選択ロジック自体ではなく、入力となる「想定秒数」が誤っているために誤ったバケットが選ばれている、というのがポイントである。

## 提案する設計 (Proposed design)

### パラメータ調整方針

- `chars_per_second` のデフォルトを `5.5` に変更する。
- `seconds_padding` は当面 `1.5` を維持する。
- 以下を一括で同じデフォルトに揃える (コード詳細は書かない、適用対象のみ列挙):
  - `openai_api_server.py` の CLI デフォルト値
  - `start_openai_server.sh` の起動引数
  - launchd plist の引数
  - 関連ドキュメント / テスト

### なぜ 5.5 か (なぜ 6.0 ではないか)

- 実測値は約 `5.37 chars/s`。
- `6.0` まで上げると実測値より積極的に「速い」前提を置くことになり、想定秒数が短く見積もられすぎて、生成中に音声が末尾で切れる (truncation) リスクが上がる。
- 一方で `5.5` は実測の `5.37` を僅かに上回る程度であり、実測ばらつき (テキスト調・句読点・指示文) を `seconds_padding = 1.5` 側で吸収できる範囲に収まる。
- 第一段の調整としては、過剰見積もりを縮める効果を得つつ truncation リスクを抑える `5.5` が安全な選択である。
- `6.0` はリスニングテストで truncation が発生しないことが確認できた段階で初めて検討する。

## 期待される効果 (Expected effect)

新しい `chars_per_second = 5.5`, `seconds_padding = 1.5` を適用した場合の見積もり:

- 135 文字 → 約 `135 / 5.5 + 1.5 ≒ 26.0s`
- 159 文字 → 約 `159 / 5.5 + 1.5 ≒ 30.4s` (≒ 30.5s)

このため、トークン制約 (T バケット) が許す限り、同じ 294 文字サンプルは:

- 現状: `S1024 / S1536`
- 期待: `S1024 / S1024`

に収まることが期待される。これにより:

- `generation-seconds` は現在の `77s` から、おおむね `56.5s` 前後まで短縮される見込み。
- 実測 WAV 長 `54.68s` を考えると、これは「実生成時間に近い」水準まで近づくことを意味する。
- API 全体の所要時間 (`92.97s`) も連動して相応に短縮されるはず。具体的な目標値は実測で確定する。

## リスク (Risks)

- `chars_per_second` を上げ過ぎると、想定秒数が実発話より短くなり、末尾で音声が切れる (truncation) 危険が増える。
- テキストの種類 (説明調 / 会話調 / 箇条書き / 指示文)、句読点の量、感情表現などにより、実速度は変動しうるため、`5.37` という単一の実測値だけを根拠に上限まで攻めるのは危険。
- 短いセグメントが多数生成されるケースでは、`seconds_padding = 1.5` がチャンクごとに加算されるため、合算で見ると無視できないオフセットになる可能性がある (ただし今回の主目的はバケット選択の正常化なので、padding 側は据え置き)。

## 検証計画 (Validation plan)

1. ユニットテスト
   - 設定デフォルト値のテストを `5.5` に追従させる。
   - セグメントプランニング (想定秒数算出 → S バケット候補) のテストで、代表的な文字数 (例: 135, 159, 294) における選択バケットを固定する。
2. 局所テスト + 全体テスト
   - 影響範囲 (duration estimation / segment planning / bucket selection) を中心とした targeted test を流す。
   - 続けてフルテストを通す。
3. 実機デプロイ + 実測
   - 同じ 294 文字テキストで再リクエストし、レスポンスヘッダおよびログから次を確認する:
     - `backend = coreml-stateful`
     - フォールバックが発生していないこと
     - `generation-seconds` がおおむね `55–60s` の範囲に収まること
     - 採用された S バケットが理想的には `S1024 / S1024` であること
     - 出力 WAV が末尾で truncation していないこと

## ロールアウト (Rollout)

- 変更は 1 つの小さなコミットにまとめる (`chars_per_second` デフォルト統一 + テスト追従)。
- デプロイは次のコマンドで行う:
  - `scripts/irodori-openai-service.sh --timeout 900 deploy`
- まずは `5.5` をベースラインとして運用する。
- リスニングテストで truncation が一切発生しないことが確認できて初めて、`6.0` への引き上げを検討する。

## 受け入れ基準 (Acceptance criteria)

- PyTorch フォールバックが発生しないこと。
- サンプル音声で audio truncation が発生しないこと。
- 294 文字サンプルが「duration の過大評価のみを理由に `S1536` を選ぶ」状態にならないこと (T バケット制約で `S1536` が必要なケースは別問題として扱う)。
- 短いテキスト (例えば数秒程度のもの) が引き続き `3–5s` クラスに収まること。
